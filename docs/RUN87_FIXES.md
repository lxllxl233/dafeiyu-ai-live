## 1. 口径 v2：先定分母，再谈百分比

### 1.1 为什么必须换口径（run86 报告 §3 的两处硬伤）

| 旧口径行为 | 后果 | 证据 |
|---|---|---|
| 入伤只排除 `forecast.clear`，不看 `after.screen` | **逃跑/死亡也算进分母**：f19t5（盗贼逃跑 + 燃烧之血回 6）记成「预测 0、实际 −6」；f23t5（致死夹到 0）记成「预测 29、实际 7」 | 账本两条记录的 `after.screen` 分别是 `REWARD` / `GAME_OVER`，而 `forecast.clear` 都是 `None` |
| 不区分「敌方打我的血」与「我自己花掉的血」 | 血墙/放血的 2 点自扣被算成「敌人多打 2 点」：f14t4、f15t1、f17t3、f17t6、f19t3、f22t2 六条全部记成偏差 | 六条的 `forecast.self` 都是 2，`before.hp − after.hp` 都等于 `take + 2` |
| 斩杀按**数组下标**配对 | 同批先打死一只 → 幸存者重新编号 → 「下标还在」被判假斩杀（run86 5 条） | §2 逐条 |
| 反过来：`clear` 标记本身会误伤 | f9t2 打死 GREMLIN_MERC 后**分裂**出两只新怪，`forecast.clear=1` 但战斗继续；旧口径把它整条排除，等于白丢一条正确样本 | f9t2 `after.screen = COMBAT`，敌人从 1 只变 2 只 |

### 1.2 v2 的定义（`tools/accuracy.py` docstring 同步）

- **总体**：`outcome == "executed"`。被护栏拒绝/批量报错没有真实结算，不进精度统计（批次另算）。
- **入伤**：`ended=1` + `forecast.take` 非空 + 前后血量可读 + **这一批之后战斗仍在继续**（`after.screen == "COMBAT"`）。
  实际入伤 = `before.hp − after.hp − forecast.self`。
  - 排除「战斗结束」记录（`after.screen` 不是 COMBAT，或无 screen 但有 clear）→ 单列**排除桶**，**不删记录**；
  - `forecast.self`（血墙/放血/祭品）是我自己付的代价，不算敌方伤害；
  - 狱火 tick 保持在 `take` 里（它是回合开始扣血，属于模型必须预测的项）。
- **血量**：同一批记录范围；实际 = `after.hp`。`forecast.hp` 在 sim 打牌阶段就已经扣过 `self`，**不能再补**（旧草稿补过一次，5 条自扣记录全部差 −2，当场暴露）。
- **斩杀**：`forecast.kill` 的下标 → 翻译成该下标在 `before` 里的 `enemy_id` → 用**同 id 数量差**（`before − after`）核销。
  - `confirmed`（按 id 唯一，`before` 里这种怪只有 1 只）/ `confirmed`（同种怪计数，标签 `basis=count`）/ `false` / `undecidable`；
  - `after` 没有敌人列表时：只有「预测清场 + 战斗确已结束」才算确认，否则 `undecidable`（不硬凑）；
  - **无法判定既不算确认也不算假斩杀**，单独计数；
  - 同 id 多只只能确认「少了一只」，这是 `enemy_id` 无法区分的物理上限，不假装能区分。
- **未预测死亡**：`after` 有列表且某 id 减少、但没有对应预测 → 记一笔；带 `MINION_POWER` 的怪单列（随主人撤场，不算漏杀机会）。
- **批次**：`outcome == "batch_error"` / `executed`。`rejected_*` 是执行前拦下、没有半路断供，不进分子；
  但 `rejected_clear_overflow` **单独计数并打印**，因为它和 batch 中断是同一类错误的两种收尾方式（§5.3）。

## 2. P12：斩杀配对审计（20 条预测，逐条落到原始记录）

### 2.1 旧口径为什么会误报

`forecast.kill` 记的是「这一步打死的是**下标** i」。批次打完后再读一次状态，敌人的 `index` 是**重新排过的**。
只要这一批里有怪先死（分裂、蛋爆、爪牙撤场、多怪先后死），存活者的下标就会前移，「下标 i 还在」这句话就再也不代表「我打的那只还在」。

### 2.3 20 条预测的完整分类（`--audit` 可复现）

- 预测 20 次 → **确认 20（id 唯一 15 + 同种怪计数 5）· 假斩杀 0 · 无法判定 0**；
- 旧口径对照：确认 15 · 假斩杀 5；
- 20 条里 11 条是「清场」记录（`forecast.clear=1` 且 `after.screen=REWARD`），按「战斗结束」证据计确认；
- 未预测死亡 0 只；爪牙撤场 0 只；战斗结束导致不可判定 2 条（f19t5 逃跑、f22t7 的第二次尝试）。

**判定：run86 的 5 条假斩杀是 100% 统计误报，不是模型把活怪当死怪。** 但——

### 2.4 残留风险（不许因为 0 就宣称可靠）

1. **同种怪计数会掩盖「打错目标」**：如果模型预测杀 A 只 21 血蛋、实际死的是 9 血蛋，计数照样是 3→2 → 判确认。
   缓解：`basis=count` 单列（run86 是 5/20），并人工做血量交叉验证（上表两条都做了）；**没有自动手段能排除**，
   因为引擎不给每只怪 uuid。
2. **「假斩杀 0」≠「斩杀判断强」**：这个指标只验「说了能杀、结果真死了」，不验「能杀的时候有没有放跑」。
   `未预测死亡 0` 也不代表没有漏杀机会 —— run86 的漏杀只能靠离线搜索斩杀线来查，**至今没做**（§9.1）。
3. 若将来一次批次里同时发生「预测杀死 X + X 同种怪里另一只死」，v2 会判确认，**宁可漏报也不误报**。这是有意的取舍。

## 4. P10：奖励屏 DECK_CAP 死锁

### 4.1 死锁链（三处叠加）

1. `deck_cap_guard()` 在牌组 ≥ 上限时拦 `choose_reward_card` 和 `collect_rewards_and_proceed`；
2. `pending_card_reward()` 用「`rewards` 里还有一张没领的 Card」推断「正在等选牌」——
   **skip 之后这张 Card 依然是 `claimable`**，于是永远返回 True；
3. 于是「拦 collect → 提示先 skip → skip 完再 collect → 还拦」形成闭环：奖励收不掉，也进不了下一层。
   run86 f21/f22 的 `DECK_FAT 牌组 18 张 > 上限 16` 就是这个状态。

### 4.2 根因 B：牌组上限算错一幕（act_id 是 0 基）

- 账本证据：`run.act = "1"`、`run.act_id = "0"`（第一幕）／`act = "2"`、`act_id = "1"`（第二幕）—— **act_id 是 0 基**。
- 旧代码 `deck_cap(run.get("act_id", run.get("act")))` 把它当 1 基 → 第二幕按 16 张算（该 18）、第三幕按 18（该 20）。
  run86 第二幕一进 f13 就「满编」，等于**提前两张锁死拿牌**，还触发了 `DECK_FAT` 的错误文案。
- 修法：新增 `sts2.run_act(run)`（`act` 1 基、`act_id` 0 基，各自换算成 1 基），`deck_cap` 只接受 1 基；
  `deck_cap_guard`、`compact()` 的 `DECK_FAT`、`tools/preflight.py` 全部改用它。

### 4.3 修法与「合法满编路径」

```python
# 只认引擎的权威字段；字段缺失才退回旧判据（宁多拦一手，也不静默领牌）
for blob in (reward, state):
    if "pending_card_choice" in blob:
        return _truthy(blob["pending_card_choice"])
```

合法路径（**没有绕过上限、没有静默领牌、没有强制扩牌组**）：

| 局面 | 合法动作 | 结果 |
|---|---|---|
| 牌组 < 上限 | `choose_reward_card --option N` | 拿牌 |
| 牌组 ≥ 上限，不想要 | `skip_reward_cards` → `collect_rewards_and_proceed` | 空收，离开奖励屏（**v2 下放行**） |
| 牌组 ≥ 上限，真想要 | `choose_reward_card --force`（必须说清踢掉谁） | 拿牌（保留原逃生口，未放宽） |
| 牌组 ≥ 上限，先腾地方 | 商店删牌 / 事件删牌 → 回到 < 上限 | 再正常拿 |

额外保险：`collect_rewards_and_proceed` / `resolve_rewards` 之后比对前后牌组张数，**涨了就喊 `DECK_GREW`**
（牌组 n0→n1 + 上限 + 补救提示）。动作已经发生，所以只留痕不 abort —— 但要保证「静默领牌」不可能再无声无息。

### 4.4 验证边界（诚实说明）

- 账本里**没有 REWARD 屏记录**（决策只在战斗内记），游戏当前在 `MAIN_MENU`，所以**无法在真实奖励屏上验证 `pending_card_choice` 这个字段名**。
- 现有证据：run86 `batch.log` 里那屏真实文本 `reward[2] Card 将一张牌添加到你的牌组。` + `LEGAL collect_rewards_and_proceed`，说明「skip 后 rewards 仍有 Card」这一点是实测的。
- 为此加了 `sts2.reward_field_hint()`：**如果奖励对象里没有 `pending_card_choice`**，拦停文案会多打一行
  `REWARD_KEYS ...`（真实字段名），提示把这一行贴回文档。这样「字段名猜错」不会变成新的静默死锁。

## 5. P14：清场后追加尾牌导致 batch 中途断供

### 5.1 根因

`sts2.cmd_batch` 逐步执行，每步前重读局面。清场那一刀之后战斗**立刻结束**（进奖励屏），
第 i+1 步 `_player_turn_state()` 等 2.5 秒仍拿不到玩家回合快照 → `BATCH STOP` + `BATCH PARTIAL i/n` + `exit 3`。

run86 f21t4 原始记录：`seq = [TAUNT, THUNDERCLAP, STRIKE, INFLAME, end]`，
`steps` 里 3 张牌都算出来了（第 3 张 STRIKE 是斩杀），`batch.log[0] = "BATCH PARTIAL 3/5：前 3 步已执行"`，
`outcome = batch_error`。这一回合的**账本 truth 与计划永久错位**：模型以为打了 4 张，实际只打了 3 张。

### 5.2 修法（执行前拒绝，不截断）

- `sim.validate()` 新增 `sim.cleared_at`：某一步打完场上没活怪（幻象 `revive` 不算清场）就记下 0 基步号；
- `act.clear_overflow_error(steps, cleared)`：清场之后还有**非 end** 的动作 → 返回 `CLEAR_OVERFLOW`；
- `_execute` 在**任何动作发出前**拒绝整批，`outcome = rejected_clear_overflow`，文案给出「第几步杀了谁、后面还有几步、去掉重发」；
- `--dry` 也会提前报出来（`clear_overflow` 字段），不用等真打；
- **尾部的 `end` 允许**：账本里 11 条清场记录全是「斩杀牌 + end」形状且全部成功，sts2 的 batch 遇到这种情况会跳过 `end_turn`（`[i] end_turn 跳过：战斗已经结束`）。

### 5.3 为什么不并进 batch 中断分子

预检把「半路断供」变成「执行前拒绝」——**真正的失败模式（半批落地）消失了**，但如果把 `rejected_clear_overflow` 也塞进分子，
就成了「把错误挪个地方然后再扣分」，反过来若直接删掉就更糟。所以：

- `batch 中断 = batch_error / executed`（口径不动，run86 仍是 1/65）；
- `rejected_clear_overflow` **单列打印**；run87 报告必须同时给出这两个数。
- 历史记录里 `rejected_clear_overflow = 0`（那时还没有这个预检），f21t4 仍以 `batch_error` 留在账本里。

## 6. P15：脆弱（Frail）与格挡——引擎已经砍过，不能再砍一次

### 6.1 证据（全账本分组统计，不靠经验）

按 `(卡牌, 是否升级, 手牌时身上有没有脆弱)` 统计引擎 `dynamic_values.Block` 的取值分布：

| 耸肩无视 | 8（120） | **6**（4） | 8×0.75 = 6 |

### 6.2 旧 sim 错在哪

`sim.play()` 在 `card["blk"]` 上再乘 0.75；`sim.max_block()` 走同一路径；`sts2.hand_block_pool()`（ctx 的
`BLOCK_POOL` / `LEFT_BLOCK_ON_TABLE` 提示）也再乘一次。三处都是**重复打折** →
脆弱回合格挡低估 25% → **入伤高估** → 该挡的时候以为挡不住（run86 f12t2：预测 6、实际 4）。

### 6.3 改动

- `tools/sim.py`：删掉 `int(gain * 0.75)`；新增 `Sim._dex_block()` —— 只补**批内新加**的敏捷（快照值不含它），
  脆弱对这一小部分仍按 0.75 折（语义完整）；
- `sim.max_block()`：随 `play()` 自动同步（不再额外打折）；
- `sts2.hand_block_pool()`：不再打折，`frail` 参数保留但不再参与计算（注释写明原因）。

## 9. 未解决问题 / 风险 / 隔离方案

### 9.1 还没解决（必须在 run87 报告里继续盯）

1. **漏杀机会无法量化**：v2 只验「说了能杀 → 真死了」，不验「能杀没杀」。离线搜斩杀线（把 `lethal_targets` 的贪心换成小规模 DFS）没做。
   → 隔离：run87 的「假斩杀 0」只作为**不撒谎**的指标，禁止用它宣称斩杀判断力。
2. **`pending_card_choice` 字段未在真实奖励屏验证**（§4.4）。→ 隔离：`REWARD_KEYS` 提示 + run87 首次奖励屏必须贴字段名。
3. **未建模机制仍在**：`GORGET` / `CANDELABRA` / `PAELS_FLESH` / `MUMMIFIED_HAND` / `ORNAMENTAL_FAN` /
   `ESCAPE_ARTIST_POWER` / `PLATING_POWER` 只在 `unmodeled`/`approx` 里留痕，不建模。→ 隔离：这些局的入伤按「估算」看待，不并进硬指标。
4. **`rejected_clear_overflow` 与 `batch_error` 的边界依赖 `sim` 的斩杀判断**：如果 sim 漏杀（以为没清场），预检不会触发，
   仍然会走 batch 断供。→ 隔离：两个数一起看（§5.3），单看任何一个都会漏报。

### 9.2 已知误差源（可接受，但要写进结论）

- 同种怪多只时斩杀只能按计数确认（§2.4）；
- `replay.py` 的 PASS 数会因为模型修正而下降，它不是回归指标，是确定性指标；
- `act_id` 的 0 基约定来自 run85/run86 账本（`act="0"/"1"` ↔ `act_id="0"/"1"`），若引擎换版本需重新核对。
