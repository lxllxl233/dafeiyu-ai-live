## 1. 两个现象与根因（先证据，后动手）

| # | 用户看到的现象 | 根因（可复核） |
|---|---|---|
| A | 一句话还没说完就提前显示「思考中……」 | 窗口拿不到真实播放时长，用的是「发布时刻 + 字数估时长」；而真实播放要等 TTS 合成完才起播，估计值从**发布**那一刻就开始跑，所以必然提前 |
| B | 操作早就做完了，主播过很久才讲那一句 | ①一回合能连发多条台词，页面是严格 FIFO 播完上一条才播下一条 → 排队积压；②起播本身还要等合成 |

### A 的证据（修复前，最近 40 句）

- **40/40 句**都在音频真正结束之前就切了「思考中」；提前量中位 **4.19s**、最大 **10.58s**。
- 同批样本 `发布→起播` 中位 **2.80s**（mean 3.40s、max 8.26s），字数中位 23、音频中位 5.45s。
- 机制层面：`Speaker.delegate=1` 时窗口不自己播，`on_start` 不触发 → 窗口拿不到真实时长；
  旧实现只能拿「估计值」，锚点还是发布时刻。

### B 的证据（全量 2881 句，`tools/av_lag_report.py`）

```
TTS合成        n=2764 median= 1.85s p90= 3.09s max= 6.01s
发布→起播[record] n=2879 median= 0.02s p90= 3.61s max=22.97s
排队等待         n=2880 median= 0.00s p90= 2.07s max=20.95s (>1.5s 占 11.4%)
```

- 中位 0.02s 是因为页面/磁盘有缓存：同一句重复播瞬时起播。**问题在尾巴**：p90 3.6s、最长 22.9s。
- 把「排队等待」拆出来（`发布→起播 − 合成耗时`）：11.4% 的句子在合成之外还多等了 1.5s 以上，
  最长 **20.95s**。这 328 句里有 **326 句**发布时距上一句不到 15s —— 即**同一回合连发的多条台词**在排队。
- 旧页面是 `sleep(durMs + 120)` 的严格 FIFO：上一句 7–15s 时，新台词只能等它播完。

## 2. 修法（没有加固定延迟，也没有只在 UI 层拖延）

### A：让窗口跟随**真实播放**

新增一条「播放生命周期」事实链，谁在播、播到哪、何时结束，全部由**真正出声的那一端**上报：

1. 页面在 `src.start()` 后 `mark('audio', {dur, start_t})`，`onended` 后 `mark('audio_end')`；
2. `overlay_server.py` 维护 `_audio{seq,cid,role,since,dur,pending}`，`/state`、`/health`、
   快照里都带 `playback{seq,playing,remaining,dur,cid,role,pending,speaking}`；
3. `streamer.py` 用 `playback.seq` 单调丢弃旧帧 → `audio_started(remaining)` 把说话态续到
   **真实结束时刻**，`audio_queue(queued)` 在「还在合成/还在排队」时也保持说话态（避免空档闪一下
   「思考中」），`audio_ended()` 才清估计值；
4. `tools/caster_state.py` 的 `_resolve` 顺序：`speak_until` → `audio_until` → `thinking_on` → IDLE。
   真实播放永远压过估计值；估计值只在前端还没上报时兜底（旧页面/断线）。
5. `playback.pending`（合成中/排队中）也算说话态，TTL 15s 自动清（`STS2_AUDIO_PENDING_TTL`），
   防止页面崩了把窗口永久钉在说话态。

### B：让「该说的那句」立刻播

1. `tools/act.py`：一回合只播第一句（其余只写进日志），从源头消掉排队积压；
   调试时 `STS2_ACT_DEBUG=1` 会打印 `SAY_MERGE`。
2. 页面调度改成**最新优先**：新台词来了，若旧句还没出声（还在合成）→ 直接作废；
   已出声且播超过 `PREEMPT_MS=800ms` → 切新句（新句合成期间旧句继续响，不留空白）；
   超过 `STALE_MS=9000ms` 的旧台词直接丢，并 `mark('skip',{why:'stale'|'superseded'})` 留痕。
3. `index.html` 加 `UI_VER` + `mark('hi',{ver})`：每个页面加载时报一次版本，日志里能确认
   「播的是新前端还是旧缓存」。`overlay_server` 快照带 `ui_rev`（index.html 的 mtime-size），
   页面空闲时发现 `ui_rev` 变了就自动 `location.reload()`，以后改前端不用手动刷 OBS 源。

## 6. 剩余风险 / 坑

1. **直播姬里的那个页面不会自动刷新**：它跑的还是旧前端（日志里只有 `role=record` 有
   `hi ver=2026-10-27b`）。旧前端仍会被服务端的 `playback` 正确驱动（A 类已修），
   但它自己的 FIFO 队列还在 → B 类要靠「一回合一句」兜住。**刷一次直播姬源**就完全一致了。
2. `_audio` 的 pending 只活 15s；若某页面卡死不上报，窗口会在 15s 后回落，不会永久卡住。
3. TTS 仍是「整句合成完再播」，起播延迟下限 ≈ 合成耗时（中位 1.85s）。要再快只能流式/分段合成，
   风险高（本机听不出问题就会翻车），本轮**故意不做**，记录为后续空间。
4. 估计值兜底仍在（旧页面、页面崩溃、无 marks），公式见 `caster_state.estimate_seconds()`；
   真实音频一旦上报就压过估计值。
