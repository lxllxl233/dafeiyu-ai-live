# 铁甲战士 A10 · 决策 OS v23

> 本文件是 Slay the Spire 2 铁甲战士 A10 的长期决策手册。
>
> **运行时提示词**：`games/slay-the-spire-2/decision/prompts.py`
>
> **硬规则源**：`games/slay-the-spire-2/decision/hard_rules.py`
>
> **规则一致性**：`tools/test_docs_consistency.py`
>
> **回归测试**：`tools/test_regressions.py`
>
> **决策目标**：提高 A10 通关率，减少无效操作、算账错误、执行卡死和重复犯错。
>
> 本文是决策规范，不代表所有机制已经在代码中实现。涉及引擎行为、伤害公式、费用变化、界面状态和自动执行的规则，必须以实际游戏状态及经过验证的代码为准。

## 0. 总体决策原则

### 0.1 目标函数

决策按以下优先级优化：

1. **避免死亡**：处理致死伤害、无法承受的持续伤害和危险的延迟结算。
2. **寻找确定性胜利**：存在经过验证的斩杀线时，优先评估斩杀及其附带效果。
3. **避免重大损失**：在不能斩杀时，比较格挡、药水、控制、换血和其他可行方案。
4. **提高战斗效率**：在生存风险可控的前提下减少战斗回合和损失的生命。
5. **投资未来回合**：在当前回合安全的情况下，构建力量、格挡引擎、抽牌和能量循环。
6. **优化整局胜率**：综合考虑牌组、遗物、药水、生命、路线、金币和后续 Boss。

不允许把某一项固定为绝对优先级。例如：

- 斩杀不一定安全：敌人可能在死亡时触发效果。
- 全挡不一定最优：能够可靠斩杀并阻止敌人行动时，斩杀通常更有价值。
- 输出最大化不一定最优：敌人本回合不造成伤害时，不应无收益地堆甲。
- 保留药水不一定最优：药水能避免死亡或显著减少损失时，应优先考虑使用。
- 结束时能量为零不代表操作正确：不能为了消耗能量而打出低收益甚至有害的牌。

### 0.2 证据等级

所有决策信息按可靠程度处理：

| 等级 | 来源 | 使用方式 |
|---|---|---|
| E0 | 当前游戏引擎返回的状态、可执行动作及明确错误信息 | 执行和校验的主要依据 |
| E1 | 当前 `ctx` 的实测字段、费用、伤害、格挡、敌人意图 | 主要决策依据，必要时交叉核对 |
| E2 | `plans`、模拟器、规则表和经过回归验证的计算结果 | 用于比较候选行动；注意模拟边界 |
| E3 | 长期决策手册、卡牌资料、历史教训 | 补充解释和指导 |
| E4 | 口算、经验猜测、模型推断 | 只能作为待验证假设 |

当高优先级证据与低优先级推断冲突时，先检查状态是否过期、字段是否具有相同语义，以及计算是否覆盖了全部效果。不得为了迎合手册而忽略当前实际状态。

### 0.3 决策分层

每次行动依次经过四层：

1. **状态层**：当前处于什么界面、什么回合、哪些动作有效。
2. **合法性层**：目标是否存在、费用是否足够、卡牌和药水是否可用。
3. **战术层**：斩杀、生存、格挡、换血和铺场的比较。
4. **执行层**：逐步执行、核对结果、处理失败并恢复。

任何一层未通过，都不能直接进入下一层。

## 1. 传输协议与执行纪律

### 1.1 一回合的基本协议

标准流程：

```text
读取当前 ctx
    ↓
检查状态有效性和警告
    ↓
计算候选行动
    ↓
生成 seq 和可选 fx
    ↓
执行 act
    ↓
读取 act 返回的下回合 ctx
    ↓
根据实际结果决定下一步
```

命令：

```bash
python tools/ctx.py
python tools/act.py --file tmp_plan.json
```

正常情况下，`act` 返回的 `ctx` 就是下一次决策的输入，不要无意义地重复读取状态。

以下情况必须重新读取 `ctx`：

- 新战斗开始、换幕或切换界面。
- 出牌失败，返回 `ok:false`。
- 出现 `stale_ctx`。
- 手牌处于抽牌或更新过程。
- 药水进入 `CARD_SELECTION` 等待选择状态。
- 返回结果与预期不符，无法确定当前实际状态。
- 自动执行停止，但停止原因或下一步动作不明确。

### 1.2 输出格式

示例：

```json
{
  "say": ["先上易伤，再让痛击收尾。"],
  "seq": [
    {"c": "BASH", "t": 0},
    {"c": "STRIKE_IRONCLAD", "t": 0},
    {"end": 1}
  ],
  "fx": {
    "e": 0,
    "hp": 59,
    "take": 0
  }
}
```

规则：

- `c` 使用 `card_id`，不使用手牌下标。
- 升级卡使用项目实际支持的 ID 格式。
- `t` 使用当前敌人下标；只有在目标可以被可靠确定时才省略。
- `p` 使用药水槽位，目标型药水必须提供有效的 `t`。
- `end` 表示结束回合，应作为最后一步。
- 不写 `end` 表示尚未结束回合，必须根据执行结果继续判断。
- `fx` 只报告执行器实际支持和校验的字段。不能确定的字段宁可省略，不得伪造。
- `say` 只写 1 句（数组长度 1），简短解释关键决策，不复述整份账本，不念无意义的血条。
- `say` 中的承诺必须与 `seq` 一致。例如，计划斩杀却没有可靠斩杀线时，不得宣称一定击杀。

### 1.3 执行失败处理

收到 `ok:false`：

1. 停止沿用原计划。
2. 读取返回的错误信息和当前 `ctx`。
3. 判断失败原因：费用不足、目标无效、状态过期、界面变化、前置选择未完成或其他执行错误。
4. 根据当前实际状态重新计算。
5. 只提交修正后的剩余动作。
6. 只有确认回合尚未结束且状态有效时，才继续出牌。

**禁止在失败后自动补上 `end` 或 `end_turn`。**

如果执行器返回的 `ctx` 不足以判断当前状态，先调用 `ctx.py`，不得猜测。

### 1.4 自动执行边界

`auto` 仅用于已经验证适用的普通战斗，不得将其视为无条件安全的批量执行机制。

适用条件：

- 非精英、非 Boss。
- 没有尚未验证的特殊死亡效果。
- 不存在需要精准控制的多怪机制。
- 当前生命与预测伤害留有足够安全余量。
- 执行器可以在危险状态、战斗结束、奖励选择或界面变化时可靠停止。

示例：

```json
{
  "auto": {
    "turns": 3,
    "stop_hp": 40
  }
}
```

实际参数、停止条件和支持范围以执行器实现为准。自动执行中发生异常时，必须停止批量动作并重新读取状态。

## 2. 状态可信度与战斗前检查

每回合开始，按顺序检查：

1. 当前界面、回合和战斗状态。
2. `stale_ctx`、`mid`、`pending` 等状态标记。
3. 当前生命、格挡、能量和费用修正。
4. 药水槽、遗物、力量、敏捷、覆甲及其他状态。
5. 敌人数量、生命、格挡、意图、特殊机制。
6. 当前手牌及抽牌、弃牌、消耗牌堆。
7. `warn`、`calc`、`plans` 和候选行动。
8. 本回合可执行动作及执行器约束。

### 2.1 状态一致性

以下情况属于高风险状态：

- 手牌数量与实际动作不一致。
- 能量值与费用计算不一致。
- 敌人已死亡但仍出现在候选目标中。
- 界面已经变化但仍尝试执行战斗动作。
- 药水使用后进入选牌界面，却继续打牌。
- 已经结束回合，却仍尝试追加操作。

出现以上问题时，不允许依靠记忆或旧 `ctx` 继续决策。

### 2.2 `hand_n` 与合并手牌

`hand_n` 表示真实手牌数量。`hand[]` 可能合并同名卡牌，不能把数组条目数量直接当成实际手牌数。

同名卡牌的费用、升级状态、效果及选择规则必须与执行器一致。不得假设“最便宜/最强”的选择规则对所有卡牌和所有效果都正确，特殊牌应单独核实。

## 3. 战斗决策主流程

每回合严格执行以下步骤。

### 第一步：建立当前状态

记录：

```text
当前生命、最大生命、格挡、能量
手牌、药水、遗物和状态效果
所有敌人的生命、格挡、意图及特殊机制
本回合入伤、回合结束后的持续伤害
下回合预计入伤和可能的抽牌收益
```

### 第二步：计算敌人威胁

对每个存活敌人，分别判断：

- 当前回合是否实际造成伤害。
- 伤害是否多段、AOE 或带特殊结算。
- 是否存在召唤、增益、塞牌、死亡效果或控制。
- 击杀它能否阻止本次或后续行动。
- 是否具有可利用的眩晕、无实体、滑溜、荆棘等机制。
- 下回合是否会出现更危险的攻击。

不能只看第一只敌人，也不能只看最高攻击数字。

### 第三步：建立候选行动

至少比较适用的方案：

- A：可靠斩杀或控制。
- B：最大限度降低死亡风险。
- C：使用药水后斩杀或保命。
- D：优先处理最危险的敌人。
- E：在可接受的生命损失下换血。
- F：安全铺场，为后续回合构建优势。

如果某方案明显不可行，可以跳过，但不能仅凭主观感觉认定某方案不可行。

### 第四步：逐步模拟

每张牌或药水执行后，更新：

```text
剩余能量
手牌与抽牌结果
敌人生命、格挡和状态
玩家生命、格挡和状态
遗物触发、消耗、召唤及死亡效果
剩余可执行动作
```

必须区分：

- 已经发生的效果。
- 当前动作结算中的效果。
- 仅在回合开始时触发的效果。
- 仅在回合结束时触发的效果。
- 下回合才生效的效果。
- 取决于随机目标或随机抽牌的效果。

不能将尚未生效的能量、伤害或格挡提前计入当前账本。

### 第五步：比较方案

按以下顺序筛选：

1. 排除非法动作和状态不可靠的方案。
2. 排除无法覆盖确定性致死风险的方案。
3. 识别可靠斩杀及其附带效果。
4. 比较剩余方案的生命损失、药水成本和后续风险。
5. 在生存相近时选择更高的有效伤害与更好的后续状态。
6. 在战斗安全时考虑铺场与长期收益。

### 第六步：输出计划

生成最短、可验证的 `seq`，必要时提供 `fx`。

不要把整手当成一个不可分割的动作包。对于复杂回合，优先使用逐步可校验的行动序列。

### 第七步：结果核对

执行后检查：

- 是否按预期打出了牌。
- 实际能量与预计能量是否一致。
- 实际伤害与预计伤害是否一致。
- 敌人死亡、眩晕和其他状态是否符合预测。
- 当前回合是否结束。
- 是否出现新的警告或界面状态。

若有差异，优先修正状态和计算逻辑，不要直接将差异归因于随机性。

## 4. 费用、伤害与格挡的计算规范

### 4.1 能量账本

维护逐步账本：

| 步骤 | 动作前能量 | 实际费用 | 其他能量变化 | 动作后能量 |
|---|---:|---:|---:|---:|
| 1 | E0 | C1 | G1 | E1 |
| 2 | E1 | C2 | G2 | E2 |
| 3 | E2 | C3 | G3 | E3 |

计算关系：

```text
动作后能量 = 动作前能量 - 实际费用 + 本步骤实际生效的能量变化
```

此处的“实际费用”必须考虑：

- 当前卡牌的实际费用。
- 临时减费或增费。
- X 费牌的实际支付。
- 费用变更牌对后续卡牌的影响。
- 触发时机和目标限制。
- 牌被消耗、打出或其他行为所触发的效果。

禁止将未来才生效的能量提前加入当前步骤。

### 4.2 费用与牌序

以下是需要验证适用条件的常见排序规则，不是无条件固定排序：

- 抽牌前先检查抽牌牌本身的费用和效果。
- 可能改变其他牌费用的牌，应先确认它对后续牌的实际影响。
- 需要保留费用的终结牌，应避免提前耗尽能量。
- 需要先建立力量、易伤等增益的牌，应与直接攻击的收益比较。
- 能量药水应在确定需要且目标回合合适时使用。
- 需要支付生命的回能牌，应在确认自伤可承受且回能能改变结果后使用。
- 需要消耗牌的引擎，应在消耗前确认引擎已经生效。

具体卡牌的特殊排序以 `references/cards.md` 和经过测试的实现为准。

### 4.3 伤害计算

优先使用当前 `ctx` 提供的实际伤害数据。手工公式仅用于交叉核对。

核对内容：

- 基础伤害与升级差异。
- 力量、虚弱、易伤和其他修正。
- 敌人格挡。
- 多段攻击的逐段结算。
- 特殊减伤、单段封顶和无实体等机制。
- 荆棘反伤及攻击触发效果。
- 击杀后的死亡效果、召唤与其他触发。
- 随机目标和随机伤害。

不能将状态牌造成的持续伤害直接当成攻击伤害。不能将未发生的回合结束伤害提前结算，也不能忽略已确定的回合结束伤害。

### 4.4 格挡计算

区分：

```text
本回合获得的格挡
本回合实际承受的攻击
格挡吸收后的剩余伤害
格挡对持续伤害或特殊效果的适用范围
回合结束时保留或清除的格挡
```

对于多段攻击，必须按照引擎的实际结算规则处理每一段。

`calc.blk`、`calc.net`、`calc.full` 等字段的具体语义，以 `references/ctx_fields.md` 为准。不得仅凭字段名称推测它们之间的计算关系。

### 4.5 模拟与实测不一致

当模拟伤害、费用或格挡与实际执行不一致时：

1. 停止使用该模拟结果作为确定性斩杀证明。
2. 记录动作前状态、预期结果和实际结果。
3. 最小化复现该差异。
4. 补充自动化回归测试。
5. 修复计算或字段映射。
6. 通过回归后，才恢复相关优化规则。

## 5. 生存、斩杀与换血

### 5.1 生存判断

判断是否会死亡时，必须综合：

- 当前生命。
- 当前有效格挡。
- 当前回合所有可预测的敌人攻击。
- 持续伤害和特殊结算。
- 能够实际使用的药水。
- 能够阻止攻击的可靠斩杀或控制。
- 执行动作后是否仍有时间完成防御动作。

不能仅比较单次最大攻击和当前生命。

若无法可靠确认总入伤，按保守方案处理，并优先选择能够降低不确定性的行动。

### 5.2 斩杀证明

斩杀必须有可核对的证据：

```text
目标仍存活
目标当前生命与格挡已知
攻击顺序已确定
费用可支付
伤害修正已考虑
多段及特殊机制已考虑
死亡触发已检查
```

只有满足适用条件时，才将斩杀视为确定性结果。

当存在多个目标时，必须比较击杀目标带来的实际收益，包括阻止攻击、阻止召唤、解除增益及其他后续效果。

### 5.3 斩杀不等于安全

遇到以下机制时，击杀敌人后仍需检查：

- 死亡爆炸或其他死亡伤害。
- 死亡后召唤或触发效果。
- 多怪之间的联动。
- 击杀后仍会结算的延迟攻击。
- 其他已经在当前状态中确认的死亡触发。

如果清场后仍有伤害结算，应将该伤害纳入战斗账本。

### 5.4 格挡与换血

换血是一个经过比较后允许的选择，不是固定伤害阈值下的自动行为。

比较：

```text
方案 A：全挡
方案 B：斩杀或控制
方案 C：药水后降低损失
方案 D：部分格挡并接受剩余伤害
方案 E：输出换血
```

优先选择综合损失较低且不会造成后续死亡的方案。

如果决定换血，必须说明：

- 为什么无法或不值得全挡。
- 本回合预计损失多少生命。
- 该伤害是否会影响下一场战斗或后续路线。
- 换血是否换来了足够的伤害、控制或未来收益。

不能因为手册写着“允许换血”就忽略当前实际风险。

### 5.5 旧斩杀线失效

以下事件发生后，必须重新计算斩杀线：

- 抽牌结果变化。
- 能量或费用变化。
- 目标获得格挡或其他减伤。
- 玩家获得虚弱等状态。
- 目标改变或敌人死亡。
- 随机效果产生新结果。
- 实际执行结果与预期不一致。

禁止沿用旧回合、旧目标或旧手牌下的斩杀结论。

---

## 6. 药水、遗物与特殊机制

### 6.1 药水评估

每瓶药水至少回答四个问题：

1. 它能解决什么当前问题？
2. 不使用会造成多大损失？
3. 现在使用是否会改变斩杀、生存或关键战斗的结果？
4. 保留它的预期价值是否高于当前收益？

优先考虑使用药水的场景：

- 不使用就可能死亡。
- 可以可靠完成关键斩杀。
- 能显著降低精英或 Boss 战损失。
- 当前药水效果明显优于未来保留价值。

不得把“留药水”设为默认目标。也不得因为药水槽已满就无条件浪费药水。

### 6.2 药水执行

```json
{"p": 0, "t": 1}
```

具体字段与槽位以当前执行器协议为准。

执行前确认：

- 槽位存在。
- 药水仍然可用。
- 目标有效。
- 药水是否要求选择卡牌、目标或其他对象。
- 使用药水后是否切换到待选择界面。

药水进入 `CARD_SELECTION` 等待状态时，必须完成对应选择，再读取最新状态继续行动。

### 6.3 遗物与触发效果

在模拟行动时，必须检查遗物是否会影响：

- 能量。
- 抽牌。
- 伤害。
- 格挡。
- 状态施加。
- 卡牌消耗。
- 回合开始或结束效果。

对于尚未验证的遗物联动，不得将推测值作为确定性结果。

### 6.4 特殊机制

对荆棘、无实体、滑溜、人工制品、延迟伤害、召唤、死亡触发和其他特殊机制：

1. 查明实际触发条件。
2. 判断效果发生的时机。
3. 确定是否影响当前伤害、费用或斩杀。
4. 使用已验证的模拟器或实际状态进行校验。
5. 无法确认时采取保守方案。

## 7. 多怪战斗与目标选择

### 7.1 目标优先级

一般情况下，依次评估：

1. 能够可靠阻止重大威胁的目标。
2. 召唤者、持续强化者或会显著恶化战局的敌人。
3. 可以可靠斩杀并阻止攻击的目标。
4. 本回合威胁最高且无法立即处理的目标。
5. 其他敌人。

这不是不可变的固定排序。目标优先级必须根据当前敌人意图、击杀收益、血量、格挡和特殊机制动态调整。

### 7.2 AOE 使用

比较：

- AOE 对所有目标的有效伤害。
- 单体攻击的集中伤害。
- 是否可以通过单体攻击阻止敌人行动。
- 是否会因为敌人格挡、减伤或特殊机制而降低 AOE 收益。
- 使用 AOE 是否消耗了更有价值的后续资源。

不得仅凭“敌人数量多”就无条件使用 AOE。

### 7.3 杀敌后的收益

击杀目标时重新计算：

- 被击杀敌人是否不再行动。
- 是否触发其他敌人的眩晕或状态变化。
- 是否解除召唤或强化机制。
- 是否发生死亡伤害。
- 剩余敌人的意图是否改变。

`calc.chain` 如果已经提供了经过验证的联动收益，应将其纳入比较；如果只是模拟下界或存在不确定性，则不能把它当成绝对保证。

### 7.4 两回合评估

在当前回合安全的前提下，评估下一回合：

```text
下一回合预计入伤
下一回合可用格挡
下一回合可用伤害
当前铺场带来的额外收益
当前消耗资源造成的机会成本
```

不能为了一个并不可靠的未来斩杀而放弃当前必要防御。

## 8. 路线、生命预算与资源管理

### 8.1 路线选择

每次地图决策至少考虑：

- 当前生命与最大生命。
- 到营火、商店、精英和 Boss 的距离。
- 牌组的实际战斗能力。
- AOE、格挡、输出和运转是否存在缺口。
- 药水和遗物情况。
- 路线中的不确定性与恢复机会。

低生命时，优先考虑能够恢复或降低风险的路线，但不能机械地认为某一节点在所有情况下都更好。

### 8.2 生命预算

历史经验中的固定阈值只能作为初始参考，不应覆盖实际风险计算。

路线规划时估算：

```text
预计到达下一个恢复点时的生命
预计到达 Boss 时的生命
途中精英和多怪战斗的潜在损失
营火恢复与升级的机会成本
药水对路线风险的影响
```

当预计无法以可接受的生命进入 Boss 战时，应重新规划路线。

如果模型没有足够数据估算未来伤害，应明确标记不确定性，避免输出伪精确的预测值。

### 8.3 精英准入

精英战的收益与风险需要同时比较：

- 当前生命。
- 当前牌组对该精英机制的针对能力。
- AOE、格挡、输出和运转。
- 可用药水。
- 失败的生命成本。
- 获得遗物的长期价值。

历史阈值可以用作风险警戒线，但不能替代具体敌人分析。

### 8.4 商店决策

优先补齐影响当前胜率的关键缺口。

一般评估顺序：

1. 能否购买解决核心问题的牌、遗物或药水。
2. 是否有足够金币并保留必要资源。
3. 删牌是否真正改善抽牌质量。
4. 是否会因购牌导致无法支付后续必要支出。
5. 当前商店是否值得继续停留。

对于执行器中存在的商店库存界面，必须先完成正确的界面操作，再离开商店。不能重复点击已完成的动作。

### 8.5 营火决策

比较升级与恢复的实际收益：

- 当前生命是否足以支撑后续路线。
- 升级是否改变关键斩杀、格挡或循环。
- 牌组是否已有足够的核心输出。
- 恢复能否显著降低死亡风险。

禁止把“有强牌就必升级”或“血低就必休息”写成无条件规则。

## 9. 构筑与长期规划

### 9.1 构筑目标

构筑的核心不是机械地满足卡牌数量，而是形成能够稳定运行的战斗体系。

重点评估：

- 单回合有效输出。
- 单回合有效格挡。
- AOE 与多怪处理能力。
- 抽牌与能量循环。
- 核心引擎的启动速度。
- 终结能力。
- 卡组膨胀对关键牌到达速度的影响。
- 对精英和 Boss 机制的适应性。

### 9.2 卡牌选择

每次奖励选择按以下顺序判断：

1. 能否弥补当前明显的战斗缺口。
2. 能否强化已经成形的主轴。
3. 能否与现有牌、遗物形成可靠联动。
4. 能否提高精英或 Boss 的胜率。
5. 新牌带来的收益是否高于牌组膨胀成本。

不要为了单卡强度而混合多个互相冲突的构筑方向。

### 9.3 删牌

删牌的价值是提高有效牌的抽取频率，而不是单纯减少牌数。

评估：

- 被删牌是否仍承担必要的防御或输出。
- 删牌是否改善核心牌的抽取速度。
- 是否会削弱当前关键循环。
- 是否存在更优的购牌或升级方案。
- 诅咒是否确实能够被该操作移除。

对于不能移除的诅咒，不得把删除它当成可执行计划。

### 9.4 升级

升级前评估：

- 是否改变费用。
- 是否显著提高伤害或格挡。
- 是否提高抽牌、生成资源或循环效率。
- 是否影响关键回合的斩杀线。
- 是否能在下一场重要战斗中发挥作用。

不得仅根据卡牌名称或固定排序决定升级。

### 9.5 构筑健康检查

当连续出现空费、无法有效输出或防御不足时，判断是：

- 牌组攻击能力不足。
- 费用分布不合理。
- 抽牌与循环能力不足。
- 核心引擎无法启动。
- 卡牌组合相互冲突。
- 计算或执行器出现错误。

**只有排除计算和执行问题后，才能将空费归因于牌组构筑。**

## 10. 精英与 Boss 战

### 10.1 战前检查

进入精英或 Boss 前，评估：

- 当前生命和预计承伤能力。
- 主要输出引擎是否能够及时启动。
- 格挡是否能够覆盖关键攻击。
- 是否存在应对特殊机制的牌或药水。
- 当前牌组是否有可靠的结束战斗能力。
- 预计战斗长度是否超出生命预算。

### 10.2 战斗时序

Boss 战需要同时维护：

```text
当前回合入伤
下回合预计入伤
预计剩余战斗回合
核心引擎启动所需时间
关键药水的使用时机
延迟伤害与死亡触发
```

不应只按 Boss 当前生命除以单回合伤害估算战斗长度。实际伤害会受到抽牌、费用、格挡、状态和敌人机制影响。

### 10.3 关键回合规划

对已确认的高伤害回合：

1. 计算敌人预计伤害。
2. 计算可用格挡及其他有效减伤。
3. 判断能否可靠斩杀或控制。
4. 评估是否需要提前使用药水。
5. 确保击杀不会引发更危险的死亡结算。

不能为了延迟使用药水而错过唯一有效的防御窗口。

### 10.4 Boss 失败风险

如果预测表明当前牌组无法在可接受的生命损失内击败 Boss，应在进入前重新评估路线。

已经进入 Boss 战后，不得因为过去投入了资源就继续执行明显低胜率的策略。应根据当前局面重新优化。

## 11. SL 与失败恢复

### 11.1 使用条件

SL 仅用于符合项目规则的回档场景，例如可纠正的操作失误。

使用前确认：

- 当前失败是否确实由操作错误导致。
- 回档是否能纠正该错误。
- 重开后抽牌和随机序列是否会变化。
- 当前 SL 次数是否满足限制。
- 回档是否会造成更差的状态。

不得将 SL 当成忽略正常决策风险的理由。

### 11.2 恢复流程

按实际支持的执行器接口完成：

```text
保存并退出
    ↓
继续当前运行
    ↓
重新读取 ctx
    ↓
重新计算行动
    ↓
验证回档后的实际状态
```

不得假设回档后手牌、随机结果或敌人状态必然变化。以重新读取的实际状态为准。

## 12. 工具、状态机与卡住恢复

### 12.1 状态优先

以下情况优先检查执行器和界面状态，而不是修改战术规则：

- `mid:1` 且能量为零。
- `stale_ctx`。
- 药水等待选牌。
- 卡牌奖励等待选择。
- 多选删除或变化牌。
- 商店库存尚未关闭。
- 界面已经切换但仍执行旧动作。
- 连续动作无进展。
- 相同错误重复出现。

### 12.2 卡住诊断

出现卡住时，按顺序检查：

1. 当前界面是否仍是预期界面。
2. 是否存在未完成的目标选择。
3. 是否有动作处于 pending 状态。
4. 执行器是否正在等待某个事件。
5. 当前状态是否与上次请求完全相同。
6. 是否重复提交同一条失败动作。
7. 是否存在超时、锁、循环或异步任务未完成。

恢复原则：

- 能够确定安全恢复动作时，执行该动作。
- 无法确认状态时，重新读取上下文。
- 仍然无法恢复时，停止自动执行并保留诊断信息。
- 不允许为了让程序继续运行而伪造成功结果或跳过必要状态。

### 12.3 回归要求

每次修复必须尽可能覆盖：

- 正常成功路径。
- 费用不足路径。
- 目标无效路径。
- 状态过期路径。
- 中途失败路径。
- 界面切换路径。
- 重复请求路径。
- 自动执行停止路径。

对同一故障，必须记录输入状态、预期结果、实际结果和回归测试结果。

## 13. 复盘、记忆与经验更新

### 13.1 记忆分层

- L1：开局、换幕、新 session 或固定间隔的全局记忆更新。
- L2：每回合使用最新 `ctx` 和硬规则。
- L3：战斗日志、楼层日志、战报与历史复盘。

具体命令以项目当前实现为准。

长期记忆不能代替当前状态；历史经验不能覆盖已验证的当前规则。

### 13.2 每场战斗复盘

记录：

```text
战斗前状态
关键回合输入
候选行动
实际执行序列
预期结果
实际结果
生命与药水损失
错误类型
是否能够通过代码测试复现
```

### 13.3 错误分类

| 分类 | 典型问题 | 优先修复位置 |
|---|---|---|
| 状态错误 | 使用过期 ctx | 状态读取与状态机 |
| 费用错误 | 费用或回能计算不一致 | 费用计算、执行器 |
| 伤害错误 | 斩杀线误判 | 伤害模拟器 |
| 格挡错误 | 承伤预测错误 | 格挡和敌人伤害模拟 |
| 策略错误 | 选错目标或方案 | 决策规则与提示词 |
| 执行错误 | 动作失败后仍继续 | 执行器与恢复流程 |
| 构筑错误 | 牌组缺乏输出或运转 | 长期决策与构筑规则 |
| 复盘错误 | 重复犯错或错误归因 | 记忆与测试体系 |

### 13.4 教训晋级标准

一条新教训不能因为单次失败就升级为硬规则。

晋级前至少确认：

1. 复盘结论有日志或状态证据。
2. 已排除计算和执行错误。
3. 能明确说明适用条件与例外。
4. 不会与现有规则发生冲突。
5. 可以构造可复现的测试，或有充分的重复实战证据。
6. 修改后经过回归验证。

一次性经验先记入 `references/lessons.md`，经过验证后再考虑写入本文件或运行时硬规则。

## 14. 反模式与停止条件

发现以下情况时，立即停止沿用当前计划：

1. 未读取当前有效 `ctx` 就开始决策。
2. 使用敌人或手牌的旧状态计算斩杀。
3. 没有核对实际费用就提交整手动作。
4. 将尚未生效的能量计入当前回合。
5. 把状态牌伤害误当成攻击伤害。
6. 忽略多段攻击、特殊减伤或死亡触发。
7. 只看一个敌人而忽略其他威胁。
8. 为了消耗能量打出无收益动作。
9. 斩杀预测不可靠，却宣称一定击杀。
10. 发生 `ok:false` 后继续执行原计划。
11. 回合结束后仍追加动作。
12. 药水等待选牌时继续打牌。
13. 不检查药水目标和实际槽位。
14. 将模拟器结果当成未经验证的引擎事实。
15. 计算结果与实际状态不一致，却继续使用旧账本。
16. 自动执行无法判断停止原因，却仍然继续。
17. 为了套用经验阈值而忽略当前特殊机制。
18. 将单次失败直接归因于策略，而不检查状态、计算与执行。
19. 将历史记录或模型记忆当成当前实际状态。
20. 通过增加提示词来掩盖代码层面的确定性错误。

- [ ] 已逐步校验费用和牌序。

## 16. 本季经验与待验证事项

历史经验保留在 `references/lessons.md`，包括：

- 牌组输出不足时，优先解决有效攻击与运转问题。
- 召唤型敌人需要评估长期威胁，不能只看当前回合伤害。
- 药水应根据战斗时机与预期损失使用。
- AOE、格挡、输出和引擎之间需要保持合理平衡。
- Boss 战必须提前评估启动速度、持续输出和关键回合防御。
- 自动执行只适用于经过验证的安全场景。

以下内容应视为**待实测验证的策略参数**，不能仅凭本文件认定为普遍最优：

- 固定生命百分比准入阈值。
- 固定的卡组张数上限。
- 固定的每费伤害或格挡价值。
- 固定的药水使用阈值。
- 固定的精英和 Boss 准入条件。
- 依赖敌人版本、卡牌版本或 Mod 行为的特殊机制。

对这些参数，应使用真实战斗记录、可复现测试和通关结果逐步校准。

## 17. 版本维护与发布门槛

每次修改决策规则时：

1. 明确修改属于状态、计算、策略、执行还是构筑层。
2. 确定规则的适用条件、例外和证据来源。
3. 如果属于运行时硬规则，同步检查 `hard_rules.py`。
4. 如果属于模型决策规则，同步检查 `prompts.py`。
5. 更新对应的 `references/` 文档。
6. 运行 `tools/test_docs_consistency.py`。
7. 运行 `tools/test_regressions.py`。
8. 对计算或执行器修改，增加对应的专项测试。
9. 对策略修改，使用固定日志或可复现战斗对比新旧方案。
10. 只有通过必要测试后，才更新正式版本号。

建议保留以下验证指标：

- 费用计算错误率。
- 伤害与格挡预测错误率。
- 非预期动作失败率。
- 重复请求与卡住次数。
- 误判斩杀次数。
- 不必要生命损失。
- 药水使用收益。
- 战斗胜率与 A10 通关率。

评估策略时，应尽量使用相同初始状态、相同随机序列和一致的执行条件。单纯增加规则数量、减少某一类错误或提高模拟回放通过率，都不能单独证明实际通关能力提升。

**最终原则：状态可信、计算正确、动作合法、执行可恢复、策略可验证。**

任何策略优化都必须服从这五项基础要求。
